# Сборка и кеши CI

На ветке `main` CI проверяет интерфейс и Rust-приложение на Windows,
Apple Silicon и Intel Mac. На теге `v*` сборка Windows запускается параллельно
с macOS. Задание `publish` ждёт все проверки и все сборки, собирает артефакты
текущего запуска, проверяет наличие установщиков и подписей всех трёх платформ,
затем публикует релиз и отправляет уведомление серверу.

Повторный запуск уже опубликованного тега сохраняет опубликованные файлы.
Проверка публикации повторяется непосредственно перед загрузкой файлов,
чтобы защитить релиз от двух одновременно запущенных workflow.

## Кеши

- Кеш тестовых Rust-зависимостей сохраняется только на основной ветке.
- Отдельный workflow `Release cache` запускается после успешного CI основной
  ветки. Он прогревает оптимизированные зависимости и ресурсы CLAP для каждой
  платформы. Публикация релиза его не ждёт; ключей подписи у него нет.
- При точном попадании в релизный кеш повторная компиляция при прогреве
  пропускается. Изменение зависимостей или версии Rust создаёт новый кеш.
- Модели CLAP используют общий кеш фиксированной ревизии. Обработчики имеют
  отдельные кеши по ОС и архитектуре, включая исходник `clap_features.py`.
  Восстановленные модели проверяются по SHA-256, обработчик запускается
  с пробным запросом и ограничением времени 180 секунд.
- Архивы установщиков передаются между заданиями без повторного сжатия.

GitHub разрешает тегам читать кеш основной ветки, но не кеш другого тега.
Поэтому первый запуск после изменения схемы кешей может оставаться длинным.
Прогрев также можно запустить вручную через Actions → Release cache → Run
workflow на основной ветке. Не требуется новый тег или новая версия приложения.

Rust закреплён на `1.97.1`, проверенной локально. При его обновлении нужно
изменить версию в обоих workflow; тест `tools/test_ci.py` проверяет согласованность.
Прогрев устанавливает тот же target и feature `tauri/custom-protocol`, что
и релизная сборка. Подписанное приложение каждый раз собирается из актуального
исходника и манифеста компонентов.

Время оценивается по завершённым заданиям GitHub Actions. Локальная проверка
workflow не заменяет первый запуск на настоящих Windows/macOS runners.
